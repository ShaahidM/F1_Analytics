# Data Sources (APIs and Datasets)  
**OpenF1 API:** A free, open-source F1 data API covering all sessions from 2023 onward.  It offers ~18 endpoints with live and historical data: session metadata, lap times (with sector splits), pit stops, stint/compound info, positions, weather, flags and radio logs, plus car telemetry (speed, throttle, brake, gear, RPM, DRS) at ~3.7 Hz. Responses can be JSON or CSV, and CORS is enabled for browser use.  No API key is needed for past sessions (live session data is paid), and free tier rate limits are modest (≈3 requests/sec).  A typical full session telemetry query for 20 cars is extremely large (millions of points), so filtering by session_key, driver and time window is recommended.  
**FastF1 (Python):** A popular Python library that loads F1 timing/telemetry (via the official F1 timing feed).  It provides essentially the same data (lap times, sector times, pit and stint info, weather, and detailed per-lap telemetry) for races and quals from **2018 onward**. FastF1’s **Session.laps** and **Session.get_car_data()** objects include fields like LapTime, Sector times, Compound, TyreLife (laps on tyre), as well as per-lap telemetry series (speed, throttle, brake, gear, RPM, and a “normalized track position”).  This covers 2018–2026 (and timing data may be available a couple hours after each session).  FastF1 is open-source (MIT) and free, but it requires Python use (no REST interface) and caching of downloaded data (it builds a local cache of JSON/HDF files by default).  It has no hard rate limits, but uses the F1 timing web service so care with too-frequent downloads is advised.  
**Historic Results (Ergast/Jolpica):** A separate API (Ergast, now rebranded Jolpica-F1) provides race results, lap times, pit stops, standings and schedules dating back to 1950. However, Ergast/Jolpica contains no telemetry or car performance data; it’s mainly for static results (qualifying grids, finishing positions, lap times, etc.).  (Kaggle and other repos compile such historic data, e.g. “F1 World Championship 1950–2026” datasets, but these also lack detailed telemetry.)  
**Official & Other Data:** The official F1 timing feed (used by F1TV/App) is closed to public, and any live data requires subscription or live scraping tools.  Some community datasets (e.g. Kaggle) exist but typically mirror Ergast or FastF1 data.  **OpenF1 and FastF1 together form a “free/public data first” solution:** use OpenF1 for 2023+ (including coordinates) and FastF1 for 2018–2022 (with higher telemetry resolution), falling back to lap-time-only sources pre-2018 if needed.

# Telemetry and Circuit Data  
- **Telemetry Fields:** Both OpenF1 and FastF1 provide core car signals: speed (km/h), throttle (percent), brake (percent), gear, RPM, and DRS status. OpenF1 additionally includes *location coordinates* (x, y, z in metres) at ~3.7 Hz. FastF1 provides a “normalized track position” (0–1 around lap) instead of raw x/y coordinates, since it uses the official feed (see *Circuit.get_track* or *markers* for corners).  (Acceleration isn’t given directly but can be computed from speed differences.)  Telemetry is timestamped to UTC and can be filtered by time range, session and driver.  
- **Sampling Rates:** OpenF1’s telemetry is ~3.7 Hz (≈1 sample every 0.27 s). FastF1’s data is typically denser (often 10–20 Hz from the F1 UDP stream), though users often decimate it. Regardless, both are enough to capture throttle/brake transitions and corner speeds.  Note: OpenF1’s low rate may miss very brief events (e.g. <0.3 s) and can be upsampled if needed, but high-frequency spikes (like dummies) won’t appear.  
- **Circuit Coordinates:** OpenF1’s `location` endpoint returns the car’s (x,y,z) in a track-relative Cartesian frame.  These points “trace out the path the car drove — corner by corner, lap by lap”.  The origin and axes are arbitrary per circuit, so coordinates can’t be mixed between tracks; but within one session they give the precise racing line shape (useful for overlaying on a map or analyzing corner lines).  FastF1’s “normalized distance” (0–1) or per-lap distance can align laps from different drivers on the same track, but actual geometry must be inferred or taken from OpenF1 data or an external track model.  
- **Circuit Geometry & Map:** Circuit outlines aren’t directly provided, but one can reconstruct a track map from any car’s GPS trace (OpenF1 location) for that circuit.  OpenF1’s “meeting” or “session” endpoint also provides a `circuit_key` and often a circuit image or info URL, but detailed coordinates must come from telemetry.  (FastF1’s `Session.get_circuit_info()` yields track lengths and corner names, but not x/y grids by itself.)  
- **Lap and Sector Data:** OpenF1 has a `/laps` endpoint giving for each lap: start time, sector 1/2/3 durations, intermediate and trap speeds, and sector “mini-sector” classifications.  FastF1’s `session.laps` DataFrame includes analogous fields (LapTime, Sector1Time, SpeedI1, SpeedST, etc.).  These allow comparing sector times and top speeds.  (OpenF1 notes: “Segments are not available during races” for colored sectors, but raw times/speeds are.)  
- **Weather & Track Conditions:** OpenF1’s `/weather` provides time-stamped ambient and track data (air temp, track temp, humidity, wind, rain) updated ~once per minute.  This can contextualize lap times and tire wear.  There is also a “race_control” endpoint for flags and safety-car data. (FastF1 also fetches weather per lap from its own source.) 

# Tyre and Strategy Data  
- **Tyre Compounds & Stints:** OpenF1’s `/stints` lists each driving stint with its tyre compound and lap range.  Each record has `compound` (e.g. SOFT/MEDIUM/HARD/INTER/WET) and tyre age (laps used).  FastF1’s laps have `Compound`, `TyreLife`, and `FreshTyre` columns, giving similar info per lap (so one can infer when tyres were changed).  Pit stops (OpenF1 `/pit`) give lap number, pit duration, etc..  Combining stints with pit times reveals exactly which laps had which tyres.  
- **Available Metrics:** Direct measurements of tyre wear/temperature aren’t public, so we infer.  Useful derived metrics include: lap-time vs. tyre age (a “tyre degradation curve”), lap-time delta to ideal (fastest same-compound lap), average cornering speed vs. tyre age, and brake/throttle usage patterns.  For example, one might plot lap times over a long stint to estimate seconds-lost-per-lap; or compare two drivers’ sector times on equal-aged tyres.  Throttle fraction or coasting time (from telemetry) can gauge aggression and presumably tyre saving.  Another idea is a “tyre-preservation index,” e.g. quantifying how much slower a driver is in braking zones vs. their fastest pace, as a proxy for saving tyres.  
- **Confounders & Uncertainty:** Fuel load, traffic, safety cars and track evolution strongly affect lap times.  A heavy fuel load or cold tyres can mimic “slow on purpose.”  DRS usage and slipstreaming also alter speeds.  To mitigate these, analysis should: compare laps only after pit stops (similar fuel), exclude laps with traffic, and control for car position.  Strategy differences (e.g. one fewer pit stop) must be noted.  Any “tyre analysis” will be probabilistic: we would label findings as *indicative* rather than certain.  (For instance, a driver who keeps throttle lower into corners might be inferred to be saving tyres, but without telemetry slip/temperature data this is an assumption.)  Rigorous validation might use team radio transcripts or known race reports: e.g., if a driver was radioed to “manage tyres,” we can see if our metrics flagged it.  
- **Supporting Data:** Inferred metrics should combine multiple signals.  For example, a “tyre degradation graph” could plot lap time vs. lap number for each stint, highlighting the slope.  Corner-by-corner speed comparisons (e.g. entry and exit speeds at a chosen corner) can highlight who carried more speed (potentially stressing tyres).  A “driving style” profile might chart average braking percent, throttle percent, and number of upshifts per lap.  All claims must be backed by the data: e.g. “Driver A consistently braked X m/s² later than B in the last sector” or “Lap times increased by ~0.3 s/lap as tyres aged.”  Any metric should come with context (tyre compound, stint length) to avoid overstatement.

# Architecture and Stack  
- **Proposed Stack:** A common approach is a React/Next.js front end for interactive UI, with a Python backend (FastAPI or Flask) handling data queries.  Python tools (Pandas, NumPy) can preprocess and cache data.  A time-series database (e.g. PostgreSQL with TimescaleDB) or even a file-based cache (Parquet/HDF) can store telemetry and lap data.  Plotly (JavaScript or React wrapper) or D3.js are good for charts (lap time plots, throttle graphs, corner scatterplots).  The racing-line overlay can be drawn with HTML5 Canvas or SVG (Plotly can draw lines on 2D plane), or WebGL if animating many points.  Using WebGL (via a library like deck.gl or three.js) could accelerate an animated car-position replay, but for static overlays Canvas/SVG is sufficient.  
- **Data Ingestion & Normalization:** The system should routinely fetch session lists (OpenF1 `/sessions` and FastF1’s schedule) and allow the user to select Year→GP→Session.  Upon session selection, fetch/compose data: driver list, lap times (`/laps` or FastF1), stint/compound, pit stops, and telemetry for selected drivers.  Normalize field names (e.g. ensure both sources use numeric driver IDs, standardized lap indices) and align time bases (both use UTC timestamps).  Telemetry times may need alignment across cars: e.g. align two laps by track distance rather than clock time (one car might lap earlier).  Storing data per session in a local DB or cache avoids repeated downloads.  
- **Performance Considerations:** As noted, full-session telemetry is large. In practice, always query one driver at a time (OpenF1 supports filtering by `driver_number`) and restrict to the needed time range (e.g. a single lap or stint).  Index the DB on session, driver, and time to allow rapid slicing.  Caching recent queries (in-memory or Redis) can speed up repeated analyses.  Any heavy computation (e.g. generating an overlay path) should be done server-side or precomputed, with results sent to client in compact form.  Client-side visualizations (React) should avoid plotting millions of points at once; sampling or reusing SVG paths for lines can help.  Use of Web Workers or offscreen canvases may help if animating multiple cars.  
- **Visualization:** Key visuals include: **Static overlay of racing lines**, e.g. plotted (x,y) track coordinates for two drivers’ laps (different colors), possibly shaded by speed or braking.  **Speed/Throttle/Brake graphs:** charts of those signals vs. distance or vs. lap-time, overlaid per driver/lap.  **Lap time charts:** bar or line charts of lap times vs. lap number (colored by compound/stint).  **Tyre degradation graph:** e.g. lap time or delta vs. tyre age (lap count in stint).  **Corner analysis:** small multiple plots or scatter (entry vs exit speed) for a chosen corner.  **Driving-style radar or bar chart:** average throttle/brake/time at max throttle vs another driver.  **Strategy chart:** timeline of pit stops with compound labels, aligned with lap times.  All charts should allow picking two drivers and a reference (same lap# or same stint) per the desired mode (e.g. same tyre-age or same lap number).

# Roadmap, Feasibility, and Risks  
- **Data Feasibility Matrix:**  
  - *Telemetry (speed/brake/etc):* Available for 2018+ via FastF1 and 2023+ via OpenF1 (free). Earlier years: **no public telemetry**.  
  - *Coordinates (racing line):* Only via OpenF1 (2023+) or by FastF1’s limited normalized position (2018–2022). Older: none.  
  - *Lap times/sectors/pit:* Full coverage 1950+ via Jolpica/Ergast or Kaggle; aligned with FastF1 session data for 2018+.  
  - *Compound/Stint:* OpenF1 (2023+) and FastF1 (2018+) cover this. Older: lap result data might include compound (post-2000), but not in a convenient form.  
  - *Weather/Flags:* OpenF1 2023+; FastF1 2018+ usually included per lap. Historic: surface conditions only by date (no fine data).  

- **MVP (Version 1) Priorities:**  
  1. **Session Selection UI:** year → GP → session.  
  2. **Driver Selection:** list of drivers from that session (via OpenF1 or FastF1).  
  3. **Basic Comparison Views:** overlay two drivers’ racing lines on track (one lap each) with speed color-coding; simple lap time and sector time comparison (bar charts).  
  4. **Tyre Graph:** plot lap times vs. lap number (or vs. tyre age) for each driver’s stints (distinguished by compound).  
  5. **Telemetry Plot:** synchronized small charts of speed/throttle/brake for a chosen lap of each driver.  

- **Phase 2 Enhancements:**  
  - *Corner-by-corner comparison:* allow user to pick a corner (e.g. “Turn 5”) and show entry/exit speeds and delta. Data permitting, highlight differences.  
  - *Lap overlay mode:* overlay two laps’ telemetry profiles (speed/accel vs distance).  
  - *Driving-style profile:* charts of each driver’s average throttle-on percentage, brake usage per lap, gear-switch rates, etc.  
  - *Pace vs Preservation:* plot of lap time vs. some “tyre-saving index” (e.g. normalized throttle-on).  
  - *Strategy analysis:* timeline showing pit stops and stint transitions; compute “undercut/overcut” potential.  
  - *Cross-compound comparison (bonus):* e.g. show best lap on medium vs best lap on soft for each driver side-by-side.

- **Risks & Mitigations:**  
  - **Data gaps:** Pre-2018 has no telemetry; clear in UI (disable overlays for those seasons).  If broader historical is needed, focus on laps only.  
  - **Large data volume:** As noted, avoid pulling full 20-car telemetry at once.  Solution: fetch only selected drivers/laps. Cache aggressively.  
  - **Accuracy of inferences:** All tyre-management metrics are approximate. We will label these as *estimates* and possibly show confidence intervals or warnings.  We should explicitly note confounders (fuel, traffic) in tooltips or docs.  
  - **API reliability:** OpenF1 is community-run; any downtime or schema change could break the tool. Mitigation: Mirror critical data or allow FastF1 as fallback for 2023 races. Jolpica (Ergast) might evolve, so minimize hard-coding its fields.  
  - **Licensing:** All chosen sources are open/free; no known copyright issues.  
  - **Performance:** Frontend may struggle with animations or many points. Use GPU acceleration (WebGL) or progressive drawing for large tracks. Pre-compute heavy results server-side.  
  - **Validation:** Since no ground-truth tyre wear data is public, we might validate internally (e.g. check that drivers known for tyre conservation rank accordingly by our metrics) and cite research if available. Whenever possible, cross-reference lap time deltas with contemporaneous radio calls about tyres (limited availability).

Each design choice should be accompanied by disclaimers.  For example, a plot showing “relative speed vs. theoretical fastest” should note “fuel load and DRS effects not removed”. The goal is to provide *evidence-based* visual analysis, not definitive claims. With careful filtering and labeling, the tool can highlight where a driver *likely* sacrificed pace (e.g. lifting earlier or braking sooner) to save tyres, while explicitly noting that this is an inference, not a direct measurement.

**Sources:** The above is based on official OpenF1 documentation and evaluations, FastF1 documentation, and related community references on F1 data APIs. All claims about fields and coverage are drawn from these technical sources.
